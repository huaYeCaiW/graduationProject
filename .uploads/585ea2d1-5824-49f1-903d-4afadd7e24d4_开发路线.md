# 农业大棚监测与合作社服务平台 — 开发路线（v4）

## 0. 当前位置

**阶段 6（租户域与登录鉴权）已完成，2026-11-10 通过 M1 闸门。** 下一步进入阶段 7：设备 / 测点 CRUD 与 Modbus。

## 1. 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Spring Boot 4.0.8 / Java 21 |
| 消息 | MQTT（Eclipse Paho 1.2.5 + EMQX） |
| 工业协议 | Modbus TCP（模拟端 pymodbus） |

### 已收口

- 不做服务期限管理；账号是否可用只由 `user.enabled` 决定，`tenant_id` 有无即"是否已归属租户"

## 3. 里程碑

**推进原则：** 每个里程碑停下验收，闸门未过不进入下一段；不裁剪范围，但可以调整顺序。

| 里程碑 | 对应阶段 | 判定 |
|---|---|---|
| M1 租户化的监测平台 | 阶段 6 | 两个种植户交叉看不到对方数据；告警可确认 |
| M2 设备可管、协议可扩 | 阶段 7 | 增删改不重启即生效；Modbus 数据入同一条链路 |
| M3 可申请、可开通 | 阶段 8 | 申请→审批→开通→新大棚出数据；三端页面可用 |
| M4 运维、分析与交付 | 阶段 9 | 工单闭环；聚合与趋势可用；Compose 一键启动；验收留档 |

### M1 闸门（2026-11-10 通过）

- 两个租户账号分别登录，互查对方大棚返回 404/403
- 高频越限一分钟，`alarm` 表只新增 1 条 ACTIVE；恢复后自动 RECOVERED
- 跨租户的告警确认被拒绝

### M2 闸门

- 新增大棚只改数据，不改核心代码
- 逻辑删除设备后历史数据仍在，且可通过"编辑 + 启用"恢复
- Modbus 模拟从站数据与既有 MQTT 数据进入同一条处理链路

### M3 闸门

- 种植户提交服务申请 → 管理员审批 → 运维开通 → 种植户端立即可见新大棚
- 驳回必须填写说明，种植户能看到
- 超过服务项限额的开通被拒绝
- 三端页面数据刷新延迟 ≤ 3s

### M4 闸门

- 工单从发起到结案状态流转正确，种植户只能看到自己的工单
- 聚合接口按时间粒度输出 min/max/avg
- 趋势接口能判断上升 / 下降 / 平稳
- 干净环境 Compose 一条命令启动；7 天前数据被定时任务清理
- 需求文档第 9 节 12 条验收项逐条通过并留记录

## 4. 阶段计划

### 阶段 1：数据接入（MQTT + 配置）— 已完成

多设备 Paho client、QoS1、`cleanSession=false`、自动重连、重连后重新订阅、payload 指定 UTF-8；设备配置直接读库（`devices.yml` 已删），`DeviceProperties` 用 volatile Map 做快照。

**完成标准**：停掉 EMQX 再启动，MQTT 自动重连且重新订阅成功，数据恢复上报。

### 阶段 2：消息解析 — 已完成

JsonPath 提取测点值、双时间字段（payload 时间 + 系统时间）、缺时间兜底。

### 阶段 3：清洗、采样与入库 — 已完成

五步清洗、质量标记写 `point_value.quality`、采样入库节流（连续型 3-5s、事件型即入）。

**遗留**：量程校验硬编码，见"待修技术债"。

### 阶段 4：告警与阈值 — 已完成

双态 + 确认标记、告警收敛（持续越限只保留一条，更新最近值、保留首次越限时间）、启动时 `@Order(3)` 回填 ACTIVE；阈值存 `point` 表，启动加载 + PUT 修改时写库并改内存。

### 阶段 5：查询接口与设备页面 — 已完成

设备列表/详情、最新值、区间、告警、活跃告警、快照，共 7 个查询接口；`devices.html` 可提交设备。

**说明**：以上接口均未做租户过滤，过滤在阶段 6 统一补，不在阶段 5 返工。

### 阶段 6：租户域与登录鉴权 — 已完成

**已完成**

- `tenant` 表：编码、名称、联系人、电话、状态
- `user.tenant_id`（平台账号为空）、`device.tenant_id`
- 种子数据：平台租户、合作社运维账号、两个种植户账号及其大棚
- BCrypt + Session 登录：`/api/auth/login`、`/api/auth/me`、`/api/auth/logout`
- 登录成功后 `changeSessionId()` 防会话固定；失败请求不创建 session
- `Role` 枚举（`ADMIN/OPS/FARMER`），库值大写，转换集中在 `JdbcUserStore`
- `AuthConstants`：`SESSION_KEY`、权限码、`REQUEST_USER`
- `AuthInterceptor` + `WebConfig`：未登录 401；写请求按角色 403；未配规则 fail-closed；`LoginUser` 放入 request 供 `@RequestAttribute` 取
- 告警确认记录真实登录用户

**收口记录（2026-11-10）**

- 7 个查询接口全部按租户过滤：`/api/devices`、`/api/devices/{deviceCode}`、`/api/points/.../latest`、`/api/points/.../range`、`/api/alarms`、`/api/alarms/active`、`/api/snapshots`
- 分层固定为：Controller 取 `LoginUser` → Service 转 `TenantScope` → Store 执行；SQL 侧 `seeAll` 走原语句，否则拼 `d.tenant_id = ?`，不使用 `or ? is null`
- `DeviceConfig` 加 `tenantId`，`DeviceProperties` 查询补 `d.tenant_id`；快照按内存设备表过滤
- "看全部"判定为 `role == ADMIN || role == OPS`，不绑 `tenantId == null`
- 回归结果：38 项全通过（未登录 401、跨租户 404、区间越权返回空集、告警确认 403/404、双租户快照隔离、快照中文字段正确）
- 顺带修复：`device` / `point` / `tenant` 三表中文字段双重编码（latin1 误读 UTF-8 后入库），已按 `convert(cast(convert(x using latin1) as binary) using utf8mb4)` 原地修复

**完成标准**

- 两个种植户账号登录后只能看到自己的设备与数据
- 跨租户改 URL 拿不到数据
- 告警确认记录的是真实登录用户

**决策记录**

| 决策 | 结论 | 代价 |
|---|---|---|
| 隔离方式 | 单库 + `tenant_id` | 每个查询都要记得加条件，漏一处就是越权 |
| 越权返回码 | 统一 404 | 不泄露资源存在性，但排障时看不出是"没有"还是"无权" |
| 平台账号归属 | `user.tenant_id` 为空 | SQL 里要区分"平台看全部"与"租户看自己"两种分支 |
| 快照接口 | 按用户角色返回不同范围 | 最容易漏租户过滤，必须单独回归 |
| 认证授权方案 | 不引入 Spring Security，自研 `AuthInterceptor` + Session | 需自行实现会话固定防护、CSRF 缓解（SameSite=Lax）；换取不改动既有接口行为，且避免 Security 7 默认过滤器链侵入 |
| 适配器与下游 | 适配器注入 `MessageStream` 直接 `emit`，接口不设 `subscribe` | 适配器绑定下游；省去 `deviceId → Consumer` 回调表与 `disconnect` 清理 |
| 校验失败策略 | 越限只标 `BAD` 不丢弃；`verify` 返回 `PointValue` | 避免在 Reactor `map` 中抛异常终止 `share()` 热流 |
| 量程与阈值分离 | `min_value / max_value` 只作告警阈值，物理量程待加 `range_min / range_max` | 当前量程硬编码，非温度测点判定不准 |
| 服务获取方式 | 服务申请制（服务目录 → 申请 → 审批 → 开通），不设期限 | 合作社内部服务；少一套服务单据模型，但"是否已申请"只能靠 `tenant_id` 是否为空判断 |

### 阶段 7：设备 / 测点 CRUD 与 Modbus

**任务**

- `DeviceStore` 接口：`findState` / `insertDevice` / `updateDevice` / `setDeviceEnabled` / `findPointState` / `insertPoint` / `updatePoint` / `setPointEnabled`，实现放 `store/jdbc/JdbcDeviceStore`
- 六个接口：设备增/改/删，测点增/改/删；删除一律逻辑删除
- 写库成功后刷新配置快照（`DeviceProperties` 重载）
- 副作用：改协议用旧配置的适配器断开再按新配置连接；测点级改动只需刷新快照
- 恢复路径：编辑 `enabled=true`，不复用已删除的 `device_code`
- 实现 Modbus TCP 适配器；pymodbus 模拟从站：水肥灌溉（阀门状态、流量、累计用水）
- 配置声明寄存器地址、数据类型、单位、采样周期

**完成标准**

- 前端 `devices.html` 能成功提交一台新大棚及其测点，且无需重启即可采数
- 删除设备后历史数据仍在
- 重复 `device_code` 返回 409
- 新增 Modbus 设备只改数据

**易错点**

- 不用 `UPDATE` 影响行数判断存在性（驱动默认返回匹配行数，值未变也返回 1）
- 写路径不能查 `PointRefCache`（它只加载 `enabled=1`，新增测点查不到 id）
- `device_code` 逻辑删除后仍占唯一键，不能靠"删了再建同名"恢复

### 阶段 8：服务申请、审批、开通与三端页面

**任务**

- `service_item` 表与维护接口（管理员）：编码、名称、说明、大棚数上限、每棚测点数上限、指标模板、启用状态
- `service_application` 表；种植户提交申请接口（服务项、大棚数量、联系方式）
- 申请进度查询：种植户只能看自己的申请单
- 管理员审批接口：通过 / 驳回，驳回必须填写说明
- 审批通过生成 `provision_task`；运维执行开通：棚舍登记（绑定 `device_code` 与协议）、传感器配置、阈值设置、按指标模板生成测点骨架（编码/名称/单位/默认阈值）
- 开通时校验服务项限额（大棚数、每棚测点数），超限拒绝
- 开通完成刷新配置快照，设备自动进入采集；`device.application_id` 记录来源
- 三端页面：
  - 种植户端：服务申请（服务目录、提交申请）、我的大棚（棚舍状态、告警提醒、报修提交）、处理进度（申请进度、工单进度）
  - 运维端：棚舍纳管（登记、传感器配置、阈值设置）、实时监测（看板、传感器状态）、告警处理（列表、确认、收敛查看）、运维派单（接单、现场处理、完工验收）、农情分析（温度曲线、区间统计）
  - 管理端：服务配置（服务项、指标模板）、申请审批（通过/驳回说明）、账号权限（账号、角色）、数据报表（棚舍报表、告警统计）
- 统一页面骨架与请求封装，沿用 `devices.html` 的单文件风格

**完成标准**

- 从提交申请到出数据全流程无需重启
- 超限开通被拒绝
- 已存在设备可直接绑定租户，不重复生成
- 三端页面数据刷新延迟 ≤ 3s
- 按角色隐藏越权入口，但后端仍强制校验

### 阶段 9：工单、聚合与交付

**任务**

- `work_order` 表与状态机：待受理 → 处理中 → 待验收 → 已完成 / 已取消
- 种植户发起报修；运维接单派单、现场处理、提交完工；种植户确认验收；工单必须带租户过滤
- SQL 聚合：按时间粒度输出 min / max / avg；滑动窗口趋势判断（上升 / 下降 / 平稳）
- 农情日报：按天汇总每棚温湿度光照极值均值与告警次数
- Docker Compose：应用 + MySQL + EMQX + 模拟器
- 每日定时清理 7 天前数据；运维手动清理接口
- 初始化 SQL 与配置样例（含租户、服务项种子数据）
- 压测：并发测点 ≥ 100（目标 500+）、峰值 ≥ 500 条/秒、断线 5s 重连不丢
- 按需求文档第 9 节 12 条逐条验证并留记录

**完成标准**

- 双账号走通一次完整工单，种植户看不到他人工单
- 历史曲线直接用聚合结果；趋势在越限前能给出上升信号；日报与明细对得上
- 干净环境一条命令启动，全部验收项留档

```
阶段1-5（已完成）
        │
        ↓
阶段6 租户+鉴权 ─→ 阶段7 设备/测点 CRUD + Modbus ─→ 阶段8 服务申请/审批/开通 + 三端页面 ─→ 阶段9 工单/聚合/交付
```

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 租户过滤漏接口 | 越权读数据，验收第 4 条直接挂 | 阶段 6 建立"接口清单 + 逐条回归"表，每个里程碑复测 |
| 开通流程与采集链路耦合 | 新大棚开通后不出数据 | 开通完成必须刷新配置快照并触发连接，做成一条可观测日志 |
| 页面数量多（三端十几页） | 交付延期 | 阶段 8 先做"登录 + 我的大棚 + 告警"三页跑通，再补服务申请与管理端 |
| Modbus 寄存器映射调试耗时 | 阻塞阶段 7 | 先用固定寄存器表跑通，再抽象配置 |
| 逻辑删除后编码被占 | 无法重建同名设备 | 统一走"编辑 + 启用"恢复路径，页面给明确提示 |
| 服务项限额与实际设备不一致 | 开通后超卖 | 开通前在事务内校验，超额直接拒绝 |
| 单库多租户无数据库级隔离 | 一处 SQL 写错就串数据 | 所有查询集中到 Store 层，Controller 不直接拼 SQL |

3. 在 `项目笔记.md` 补一段决策代价，例如：为什么越权统一返回 404、为什么开通要刷新配置快照、为什么事件型测点不节流。
