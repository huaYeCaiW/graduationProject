## 1. 一句话目标

面向农村合作社的农业大棚监测平台：合作社把"大棚监测"作为服务提供给种植户，种植户在线提交服务申请、开通自己的大棚，平台完成多协议数据接入、清洗、存储、越限告警与农情分析。

## 2. 业务场景

合作社（平台方）负责设备采购、安装与运维；种植户按大棚数量申请服务，开通后只能看到自己的大棚数据。

主链路：

```
种植户选择服务项 → 提交申请 → 管理员审批 → 生成开通任务
→ 运维棚舍登记/传感器配置/阈值设置 → 数据开始上报 → 种植户端可见
→ 越限 → 告警提醒种植户与运维 → 确认/处理 → 报修 → 运维派单 → 工单闭环
```

三层归属关系：

```
合作社（平台）
  └── 租户（种植户）
        └── 大棚（device）
              └── 测点（point）
```

**关键约束：单库多租户。** 共享库表，靠 `tenant_id` 隔离，不引入独立 schema，也不做租户级独立部署。

- [ ] 数据清洗（校验 / 去重 / 补全 / 单位 / 时间）
- [ ] 存储与采样节流
- [ ] 越限告警（收敛 / 确认 / 自动恢复）
- [ ] 查询、聚合统计、趋势分析

## 4. 监控对象 × 数据源清单

| 监控对象 | 数据项 | 接入协议 | 采集频率 | 数据来源 |
|---|---|---|---|---|
| 大棚空气节点 | 空气温度、空气湿度、光照强度 | MQTT | 30-60s | 模拟器 / 单片机 |
| 土壤节点 | 土壤温度、土壤含水率 | MQTT | 60s | 模拟器 |
| 水肥灌溉设备 | 阀门状态、流量、累计用水 | Modbus TCP | 10-30s | pymodbus 模拟从站 |
| 棚内事件 | 卷帘/风机启停、缺水告警 | MQTT | 事件触发 | 模拟器 |

**关键约束：上报频率 ≠ 存储频率。**

数据到达后逐条实时处理（更新最新值 / 越限判断 / 清洗），连续型测点按 3-5s 采样入库一次，作为图表数据源；事件型测点到达即入库，不走采样节流。

**采集频率说明：** 表中频率是日常模拟器的运行频率。并发、吞吐、峰值指标统一延后到完整验收前压测。

## 5. 角色与权限

采用 Session 会话认证，密码 BCrypt 哈希存储。三种角色对应三端。

| 操作 | 种植户（租户） | 合作社运维 | 平台管理员 |
|---|---|---|---|
| 登录、查看实时数据 | 本租户 | 全部租户 | 全部租户 |
| 历史曲线 / 聚合统计 | 本租户 | 全部租户 | 全部租户 |
| 查看告警 | 本租户 | 全部租户 | 全部租户 |
| 确认 / 处理告警 | 本租户 | 全部租户 | ✓ |
| 查看设备在线状态 | 本租户 | 全部租户 | 全部租户 |
| 查看服务目录、提交服务申请、查看申请进度 | ✓ | ✗ | ✗ |
| 服务项配置、申请审批（含驳回说明） | ✗ | ✗ | ✓ |
| 执行开通（棚舍登记、传感器配置、生成测点） | ✗ | ✓ | ✓ |
| 新增 / 编辑 / 删除设备与测点 | ✗ | ✓ | ✓ |
| 修改测点阈值 | 本租户 | ✓ | ✓ |
| 租户 / 服务项 / 账号与角色权限管理 | ✗ | ✗ | ✓ |
| 发起报修工单 | ✓ | ✗ | ✗ |
| 接单派单、现场处理、完工验收 | ✗ | ✓ | ✗ |
| 查看数据报表（棚舍报表、告警统计） | ✗ | ✗ | ✓ |

职责划分：

- **种植户**：只关心自己的棚，看数据、收告警、确认告警、提交服务申请、报修。
- **合作社运维**：棚舍纳管、实时监测、处理告警、接单派单与现场处理、执行开通。
- **平台管理员**：管租户与账号、配置服务项与指标模板、审批申请、查数据报表。

租户隔离在服务端强制（SQL 带 `tenant_id`），前端隐藏入口只是体验优化，不作为安全边界。

## 6. 功能需求

### 6.1 租户与账号

- `tenant` 表记录种植户（名称、联系人、电话、状态）。
- `user.tenant_id` 标识账号归属；平台账号该字段为空。
- 登录使用 Session，密码 BCrypt 哈希，不存明文。
- 拦截器统一鉴权：未登录 401；跨租户访问按 404 处理，不泄露资源是否存在。
- 所有列表、详情、快照接口都在 SQL 层按 `tenant_id` 过滤，**不信任前端传入的租户参数**。
- 用户只做逻辑删除（`enabled=0`），因为 `alarm.confirmed_by / maintained_by` 有外键。

### 6.2 服务项与服务申请开通

- **服务项**：编码、名称、说明、可开通大棚数、每棚测点数、指标模板、启用状态。
- **服务目录**：种植户端展示启用中的服务项，作为提交申请的依据。
- **申请**：种植户选服务项 → 填大棚名称/数量/联系方式 → 生成申请单（待审批）。
- **审批**：管理员通过或驳回；驳回必须填写说明。
- **开通**：审批通过后生成开通任务 → 运维棚舍登记（绑定设备编号与协议）、传感器配置、阈值设置 → 系统按指标模板生成测点骨架（编码/名称/单位/默认阈值）→ 任务完成，种植户端立即可见。
- **进度**：种植户端可查看申请进度与工单进度。
- **兼容**：已接入的设备可直接挂到租户，不重复生成。
- **约束**：开通时校验服务项限额（大棚数、每棚测点数），超限拒绝。

### 6.3 数据接入

- MQTT：EMQX + QoS1 + `cleanSession=false` + 自动重连，已实现。
- Modbus：TCP 方式，pymodbus 搭模拟从站，待实现。
- 设备与协议由库配置驱动，新增 MQTT 类设备只加数据；新增协议通过实现 `ProtocolAdapter` 扩展。

### 6.4 数据清洗（五步）

| 步骤 | 内容 |
|---|---|
| 校验 | 类型、范围、空值检查，非法值丢弃并记日志 |
| 去重 | 同设备同测点同采样时间的重复消息只保留一条 |
| 补全 | 缺失字段按约定默认值或上一条有效值补全 |
| 单位 | 统一到约定单位（温度 ℃、湿度 %、光照 lux、含水率 %） |
| 时间 | 设备采样时间缺失时用服务器接收时间兜底 |

清洗结果以质量标记写入 `point_value.quality`，便于后续过滤。

### 6.5 存储

- 连续型测点每 3-5s 采样入库一条，内存保留实时最新值。
- 事件型测点（缺水、卷帘动作）到达即入库。
- 数据保留 ≥ 7 天，定时任务每日清理过期数据。
- 运维可手动触发指定时间段的数据清理。
- 逻辑删除的设备/测点不删除历史数据。

### 6.6 告警

- 越限即产生告警，端到端可见延迟 ≤ 3s。
- 状态机：`ACTIVE`（越限中）→ `RECOVERED`（已恢复）。
- 确认不是独立状态：`confirmed_by / confirmed_at` 为 NULL 表示未确认；确认只对 `ACTIVE` 生效，已恢复或不存在的告警返回 404。
- 收敛：同一测点持续越限只保留一条 `ACTIVE`，只更新当前值；`sample_at` 固定为首次越限时间。
- 恢复：数值回到阈值内自动置 `RECOVERED`，`recovered_at` 取首个正常样本时间。
- 告警查询必须按租户过滤：种植户只看自己的棚。

### 6.7 查询与分析

- 最新值查询、按时间区间查询历史。
- 聚合统计：按时间粒度输出 min / max / avg。
- 趋势分析：滑动窗口判断上升 / 下降 / 平稳。
- 农情日报：按天汇总每棚温度、湿度、光照的极值与均值，以及告警次数。

### 6.8 设备与测点管理

- 设备与测点全部存库，启动加载到内存供实时处理使用。
- 新增/编辑/删除接口仅运维与管理员可用，删除一律逻辑删除。
- 修改设备协议要用**旧配置**的适配器断开再按新配置连接。
- 测点级增删改只需刷新配置快照，不需要重连。
- 逻辑删除后 `device_code` 仍被占用，恢复统一走"编辑 + 启用"，不做复用。

### 6.9 设备在线状态

记录每台设备最后一次收到消息的时间，超过约定超时判定离线并在列表中展示。任一数据源关闭时系统正常降级、不崩溃。

### 6.10 报修与运维派单

- 种植户针对某台设备发起报修（现象描述 + 联系方式），工单状态：待受理 / 处理中 / 待验收 / 已完成 / 已取消。
- 运维接单派单、现场处理、提交完工；种植户确认验收后结案。
- 工单与设备、租户关联，结案后不可再改。

### 6.11 数据可视化（三端页面）

**种植户端**

1. 服务申请：服务目录、提交申请
2. 我的大棚：棚舍状态、告警提醒、报修提交
3. 处理进度：申请进度、工单进度

**运维端**

1. 棚舍纳管：棚舍登记、传感器配置、阈值设置
2. 实时监测：实时看板、传感器状态
3. 告警处理：告警列表、告警确认、收敛查看
4. 运维派单：接单派单、现场处理、完工验收
5. 农情分析：温度曲线、区间统计

**管理端**

1. 服务配置：服务项配置、指标模板
2. 申请审批：申请审批、驳回说明
3. 账号权限：账号管理、角色权限
4. 数据报表：棚舍报表、告警统计

### 6.12 部署

Docker Compose 一键启动：应用 + MySQL + EMQX + 模拟器。

## 7. 非功能需求

| 项 | 目标值 | 验证阶段 |
|---|---|---|
| 并发接入测点数 | ≥ 100（压测目标 500+） | 后期压测 |
| 数据频率 | 环境类 30-60s、水肥类 10-30s、事件类触发 | 后期压测 |
| 吞吐 | 峰值 ≥ 500 条/秒 | 后期压测 |
| 告警时延 | 越限到告警可见 ≤ 3s | 单机实测 |
| 可靠性 | 断线 5s 内自动重连；QoS1 不丢；异常数据清洗去重 | 后期实测 |
| 数据保留 | ≥ 7 天 | 定时任务验证 |
| 租户隔离 | 跨租户读取/写入一律 403 或 404 | 双租户交叉验证 |
| 部署 | 单机 Docker Compose 一键启动 | 交付前 |
| 扩展性 | 新增设备类型以配置为主，尽量不动核心代码 | 新增设备验证 |

## 8. 数据模型

### 8.1 已有表（见 MySQL.txt，v2.1 运行库）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `device` | 设备（大棚）主数据 | id、device_code（唯一）、name、protocol、connection_config、enabled、last_seen_at |
| `point` | 测点主数据与阈值 | id、device_id、point_code、name、address、time_address、data_type、unit、freq_seconds、min_value、max_value、enabled |
| `point_value` | 采样数据 | id、point_id、value、sample_at、sys_ts、quality |
| `alarm` | 告警记录 | id、point_id、value、threshold、limit_type、status、sample_at、created_at、confirmed_by、confirmed_at、recovered_at、maintained_by |
| `user` | 登录账号与角色 | id、username（唯一）、password_hash、role、enabled |

### 8.2 一期新增表

| 表 | 作用 | 关键字段 |
|---|---|---|
| `tenant` | 租户（种植户） | id、tenant_code（唯一）、name、contact、phone、status、created_at |

### 8.3 二期新增表

| 表 | 作用 | 关键字段 |
|---|---|---|

| `service_application` | 服务申请单 | id、tenant_id、item_id、device_count、status、remark、created_at、reviewed_by、reviewed_at、reject_reason |
| `provision_task` | 开通任务 | id、application_id、tenant_id、status、result_msg、created_at、finished_at |

### 8.4 三期新增表

| 表 | 作用 | 关键字段 |
|---|---|---|
| `work_order` | 报修工单 | id、tenant_id、device_id、type、content、status、assignee、result、created_at、finished_at |

### 8.5 对已有表的改动

| 表 | 改动 | 落地期 | 原因 |
|---|---|---|---|
| `user` | 增加 `tenant_id`（可空） | 一期 | 平台账号为空，种植户账号必须归属租户 |
| `device` | 增加 `tenant_id`（非空，默认平台租户） | 一期 | 设备即大棚，必须归属租户 |
| `device` | 增加 `application_id`（可空） | 二期 | 追溯设备由哪张服务申请单开通 |

说明：

- `point_value` 只保存 `point_id`，设备通过 `point.device_id` 关联，不冗余 `tenant_id`；租户过滤通过 join 设备表完成。
- `alarm.sample_at` 为首次越限时间，`created_at` 为落库时间，`alarm.value` 为最近一次越限值。
- `service_application.status`：`PENDING`（待审批）/ `APPROVED`（已通过）/ `REJECTED`（已驳回）/ `PROVISIONED`（已开通）/ `CANCELLED`（已取消）。
- `provision_task` 二期保留；若时间紧张可并入 `service_application` 状态，减少一张表。
- 新增表的建表 SQL 在各期落地后同步更新 `MySQL.txt`，保持"唯一真相源"。

## 9. 验收标准

| # | 验收项 | 判定方式 | 对应期 |
|---|---|---|---|
| 1 | 两个租户交叉访问，各自只能看到自己的大棚、历史、告警 | 两个种植户账号交叉请求 | 一期 |
| 2 | 4 类对象数据在页面正常刷新，延迟 ≤ 3s | 启动模拟器后观察页面 | 一期 |
| 3 | 注入异常值后 3s 内告警可见，恢复后自动转 `RECOVERED` | 构造越限/恢复数据 | 一期 |
| 4 | 跨租户直接改 URL 拿不到数据（404/403） | 手工构造请求 | 一期 |
| 5 | 种植户提交服务申请 → 管理员审批 → 运维开通 → 新大棚立即可见数据 | 完整走一遍申请流程 | 二期 |
| 6 | 超过服务项限额的开通被拒绝 | 超量开通一台验证 | 二期 |
| 7 | 设备/测点逻辑删除后历史数据仍在，且可恢复 | 删后查库 + 启用恢复 | 二期 |
| 8 | 新增 1 个设备类型只需改配置、不改核心代码 | 新增一个 MQTT 设备 | 二期 |
| 9 | 报修工单从发起到结案状态流转正确 | 种植户+运维双账号操作 | 三期 |
| 10 | 聚合接口按时间粒度输出 min/max/avg，趋势能判断上升/下降/平稳 | 接口 + 页面曲线 | 三期 |
| 11 | 并发、吞吐、采集频率指标达标 | 完整验收前压测 | 四期 |
| 12 | 干净环境 Compose 一条命令启动，7 天前数据被清理 | 空环境验证 | 四期 |

权限与安全类验收（跨租户隔离、角色越权）在每个里程碑闸门中都要回归一次，不只在对应期验一次。
