# 机房动环多元数据接入与处理系统 — 开发路线（v2）

## 1. 技术栈

| 层 | 选型 |

| 后端 | Spring Boot 4.0.8 / Java 21 / Reactor |

## 3. 里程碑

**推进原则：** 不裁剪范围，按原计划全部做完；按里程碑停下验收，闸门未过不进入下一段。

| 里程碑 | 内容 | 判定 |
|---|---|---|
| M1 核心链路 | 阶段 1-4 | 告警可入库可确认，清洗与采样生效，Modbus 数据能接入 |
| M2 管理与分析 | 阶段 5-6 | 库化设备与权限生效，聚合与趋势接口可用 |
| M3 交付 | 阶段 7-9 | 前端可用，Compose 一键启动，压测与验收通过 |

### M1 验收闸门

- 高频越限一分钟，`alarm` 表只新增 1 条 ACTIVE
- 数值恢复后自动置 RECOVERED，确认接口能写入确认人与时间
- 非法值、重复值、缺字段值均被正确处理，不污染曲线
- 0.1s 上报一分钟，连续型测点入库约 12-20 条，页面最新值仍实时
- 4 类监控对象数据进入同一条处理链路

### M2 验收闸门

- 改配置文件不覆盖库中已有阈值
- 两种角色登录后越权操作被拒绝
- 删除设备后历史数据仍在
- 聚合接口可按时间粒度输出 min / max / avg
- 趋势接口能判断上升 / 下降 / 平稳

### M3 验收闸门

- 五个页面均可正常访问，数据刷新延迟 ≤ 3s
- 告警 3s 内可见并可确认
- 干净环境 Compose 一条命令启动
- 7 天前数据被定时任务清理
- 需求文档第 8 节 10 条验收标准逐条通过并留记录

## 4. 阶段计划

### 阶段 1：告警持久化 + 收敛 + 确认（已完成）

**任务**

- 建 `alarm` 表，状态 `ACTIVE / RECOVERED` 双态，确认通过 `confirmed_by` / `confirmed_at` 标记（不设 `CONFIRMED` 状态）
- 抽 `AlarmStore` 接口（save / findActive / touch / confirm / markRecovered / findAll），实现 Jdbc 版本，保留 `@ConditionalOnProperty` 便于后续扩展
- `AlarmService` 改为只管收敛，不持有存储结构
- 收敛键 `point.id`，启动时从库回填所有 `ACTIVE` 记录
- 告警查询接口、确认接口，确认时记录操作人

**完成标准**

- 高频越限一分钟，`alarm` 表只新增 1 条 ACTIVE
- 数值恢复后自动置 RECOVERED
- 确认接口可写入确认人与时间；对已恢复或不存在的告警返回 404
- 重启后收敛状态不丢

**决策记录（阶段 1）**

| 决策 | 结论 | 代价 |
|---|---|---|
| 告警状态机 | 双态 `ACTIVE / RECOVERED` + 确认标记 | 与需求 v2 的三态不同，确认不再是终态 |
| `sample_at` 语义 | 首次越限时间，越限期间不更新 | `value` 与 `sample_at` 属于不同时刻，需在论文中说明 |
| 越限期间当前值 | 保留 `touch`，只更新 `value` | 每个越限测点每秒 1 次 UPDATE |
| 重复确认 | 覆盖上一次 | 只保留最后一次确认人，无审计 |
| 确认生效范围 | 仅 `ACTIVE` | 已恢复/不存在统一 404，不区分原因 |
| 确认接口返回 | `int` 影响行数，0 → 404 | 依赖驱动返回 matched rows（`useAffectedRows=false`） |
| 确认人来源 | 服务端常量 `TEST_USER_ID=1` | 阶段 5 必须替换为 Session 登录用户 |

### 阶段 2：数据清洗五步（已完成）

**任务**

- 校验：类型 / 范围 / 空值，非法值丢弃并记日志
- 去重：同设备同测点同采样时间只保留一条
- 补全：缺失字段按约定补齐
- 单位：统一到约定单位
- 时间：采样时间缺失用接收时间兜底
- `point_value` 增加 `quality` 字段记录清洗结果

**完成标准**

- 构造非法值、重复值、缺字段值，均被正确处理且不污染曲线
- 清洗结果可从 `quality` 字段识别

### 阶段 3：采样入库节流

**任务**

- 连续型测点每 3-5s 入库一条，内存保持实时最新值
- 事件型测点（漏水）到达即入库
- 采样调度与实时处理解耦

**完成标准**

- 0.1s 上报一分钟，库中连续型测点约 12-20 条
- 页面最新值仍为实时无延迟
- 事件型数据不丢

### 阶段 4：Modbus 适配器

**任务**

- 实现 `ProtocolAdapter` 的 Modbus TCP 版本
- pymodbus 搭模拟从站：精密空调运行状态、UPS 电压电流
- 配置声明寄存器地址、数据类型、单位、采样周期

**完成标准**

- 4 类监控对象数据全部进入同一条处理链路
- 新增 Modbus 设备只改配置
- subscribe
- 重启emqx自动重连

### 阶段 5：设备 / 点位库化 + 认证授权

**任务**

- 配置文件只作首次初始化，启动时写入库，已存在则以库为准
- 启动加载设备、测点、阈值到内存（`ThresholdLoader` 升级为统一加载器）
- 设备 / 测点增删接口，逻辑删除，历史数据保留
- `user` 表 + BCrypt + Session 登录 + 拦截器鉴权
- 按角色控制写接口：运维只读 + 告警确认 + 维护动作，决策者可增删设备测点、改阈值

**完成标准**

- 改配置文件不覆盖库中已有阈值
- 两种角色登录后，越权操作被拒绝
- 删除设备后历史数据仍在

### 阶段 6：聚合与趋势分析

**任务**

- SQL 聚合：按时间粒度输出 min / max / avg
- 滑动窗口趋势判断：上升 / 下降 / 平稳
- REST 接口暴露

**完成标准**

- 历史曲线可直接用聚合结果渲染
- 趋势接口在越限前能给出上升信号

### 阶段 7：前端五个页面

**任务**

- 登录页
- 实时数据页（设想从热流中分一路订阅）
- 历史曲线页（接聚合接口）
- 告警列表页（确认按钮）
- 设备与测点管理页（写操作仅决策者可见）

**完成标准**

- 页面数据刷新延迟 ≤ 3s
- 告警 3s 内可见并可确认
- 按角色隐藏越权入口

### 阶段 8：部署与数据清理

**任务**

- Docker Compose：应用 + MySQL + EMQX + 模拟器
- 每日定时清理 7 天前数据
- 运维手动清理接口
- 初始化 SQL 与配置样例

**完成标准**

- 干净环境一条命令启动全系统
- 定时任务执行后过期数据被清除

### 阶段 9：压测与完整验收

**任务**

- 并发测点 ≥ 100（目标 500+）
- 峰值 ≥ 500 条/秒
- 断线 5s 重连不丢数据
- 按文档第 8 节 10 条验收项逐条验证并留记录

**说明**

采集频率与吞吐指标统一放在此阶段，日常开发按文档频率运行模拟器。

## 5. 依赖关系

```
阶段1 告警 ──┐
阶段2 清洗 ──┼─→ 阶段3 采样 ─→ 阶段4 Modbus
阶段5 库化+权限 ─→ 阶段6 聚合 ─→ 阶段7 前端 ─→ 阶段8 部署 ─→ 阶段9 压测
```

阶段 1-4 是核心链路，阶段 5 之后才开始动 web 层与前端，避免反复返工。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 4 类模拟器工作量被低估 | 验收第 1 条无法通过 | 阶段 4 与 Modbus 适配器同期完成 |
| Modbus 寄存器映射调试耗时 | 阻塞阶段 4 | 先用固定寄存器表，跑通再抽象配置 |
| 阶段 5 库化改动面大 | 影响已完成的阈值逻辑 | 加载器统一改造，改完立即回归阈值 PUT 接口 |
| 前端页面多但时间紧 | 交付延期 | 先做实时、告警两页，再补历史与管理 |
| 采样节流与实时最新值冲突 | 页面数据变慢 | 最新值走内存不查库；当前内存最新值尚未保留，阶段 3 恢复节流时必须一并补回 |

## 7. 每阶段收尾动作

每个阶段结束做三件事：跑通该阶段完成标准、更新需求文档勾选状态、补一段当日笔记（重点写决策代价，例如为什么用内存 Map 做收敛、为什么事件型不节流）。
