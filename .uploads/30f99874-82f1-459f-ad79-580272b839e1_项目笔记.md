*总结*

今日搭建了底层数据框架，所有协议的数据解析后将统一成PointValue.java，目的是平衡比上下游协议差异；解析后数据直人这一种形态，更换设备或数据源类型不影响下游源码处理

- 是什么：所有协议数据解析后统一成 PointValue.java。
- 为什么：抹平上游协议/设备差异，下游只认一种形态。
- 怎么落地：适配层 + 解析层消化差异 → 产出 PointValue。

~~~java
public class MqttProtocolAdapter implements ProtocolAdapter {
~~~

### AcquisitionService

*关键功能* ：接入设备

~~~java
@Slf4j
@Service
@RequiredArgsConstructor
public class AcquisitionService implements CommandLineRunner {

    private final DeviceProperties deviceProperties;
    private final List<ProtocolAdapter> adapters;
    private final MessageStream messageStream;

    private Map<String, ProtocolAdapter> adapterMap;

    @Override
    public void run(String... args) throws Exception {
        //适配器注册表
        adapterMap = adapters.stream() .collect(Collectors.toMap(ProtocolAdapter::protocol, Function.identity()));
        //遍历设备
        for (DeviceConfig device : deviceProperties.getDevices()) {
            ProtocolAdapter adapter = adapterMap.get(device.getProtocol());
            if (adapter == null) {
                log.warn("未找到协议适配器: {}", device.getProtocol());
                continue;
            }

            adapter.connect(device);
            adapter.subscribe(device, raw -> messageStream.emit(raw));
            log.info("设备接入完成：id={}，protocol={}", device.getId(), device.getProtocol());
        }
    }
}
~~~

**总结**：机制：Reactor 热流多播（Sinks.Many）

- 是什么：一条 Flux 上挂多个 subscribe，同一份数据**同时**喂给所有订阅者

- 为什么：Cold Stream 每次 subscribe 会让上游重新发射 → 同一条报文 parse 3 次（每个订阅各跑一遍）

- 怎么落地：`Sinks.many().multicast()` 造热流入口，三路订阅共享一条 `valuesFlux`

- Hot vs Cold Stream 的区别、为什么选 Hot 而不是三个 Flux

  *完整链路* 

  AcquisitionService.run()
      → 遍历 devices.yml
      → 找 MqttProtocolAdapter (protocol="mqtt")
      → connect + subscribe(raw -> messageStream.emit(raw))
      → 定时造 RawMessage → sink.accept → messageStream.emit → rawSink.tryEmitNext
      → Reactor 热流：map(parse) → flatMapIterable → Flux<PointValue>
      → 订阅1: LatestValueHolder.update
      → 订阅2: filter(越限) → raiseAlarm → AlarmEvent → AlarmListener → AlarmService.record
      → 订阅3: sample(3s) → PointStore.save

### InMemoryPointStore

*关键功能* ：存储，查

#### save(PointValue value)

~~~java
private final Map<String, List<PointValue>> history = new ConcurrentHashMap<>();
@Override
public void save(PointValue value) {
    //拼key"th-01:temperature"
    String key = value.getDeviceId() + ":" +value.getPointId();
    //如果key不存在，new一个新的；存在返回这个list
    history.computeIfAbsent(key, k -> new CopyOnWriteArrayList<>())
            .add(value);

    log.debug("采样库存：{}", value);
}
~~~

使用Map<>+ConcurrentHashMap<>+CopyOnWriteArrayList<>()防止并发问题

CopyOnWriteArrayList关键使用在读多写少场景，写时复制整组加锁，读时无锁，list值append不中间插入删除，写是复制代价极低，concurrentHashMap的computeIfAbsent是原子的，不会并发丢list

拼key以防混淆设备

#### Optional<PointValue> findLatest(String deviceId, String pointId)

~~~java
@Override
public Optional<PointValue> findLatest(String deviceId, String pointId) {
    //拼key
    String key = deviceId + ":" + pointId;
    List<PointValue> list = history.get(key);
    return list == null || list.isEmpty() ? Optional.empty() : Optional.of(list.getLast());
}
~~~

#### List<PointValue> findByRange(String deviceId, String pointId, Instant startTime, Instant endTime)

~~~java
//查某时间范围内值
    @Override
    public List<PointValue> findByRange(String deviceId, String pointId, Instant startTime, Instant endTime) {

        //拼key"th-01:temperature"
        String key = deviceId + ":" + pointId;
        //取数组
        List<PointValue> list = history.get(key);
        if (list == null) {
            return Collections.emptyList();
        }
        return list.stream()
                .filter(pv -> !pv.getTimestamp().isBefore(startTime)
                                     && !pv.getTimestamp().isAfter(endTime))
                .toList();
    }
~~~

!pv.getTimestamp().isBefore(startTime)取反是为了< 变 >= 开区间转为闭区间

关键代码：history.computeIfAbsent(key, k -> new CopyOnWriteArrayList<>())

含义：查是否有相同key的list没有就新建一个CopyOnWriteArrayList()，返回值list。save()需写操作，所以需要computeIfAbsent，其他两个方法只读在没有这个key时返回empty就行不需要创建

## 2026.10.31 部分总结

CHM与桶级锁：`ConcurrentHashMap`采用桶级锁，当A线程操作某个桶时，只锁当前节点，不影响B操作其他桶，并发度极高。

CHM的`compute`方法：使用`compute`是为了保证符合操作的原子性。当相同Key的请求并发进入时，通过底层加锁排队，避免A线程执行一半被B线程读到旧数据，从而引发竟态条件（防止去重失效）

线程池与组件自洽：项目中的线程池是由引入的组件（入Tomcat、Reactor、HikariCP）各自维护的，线程数量有各组件内部默认配置决定。

阻塞与任务堆积：单个工作线程被阻塞，不影响其他空闲线程处理任务；但当线程内所有线程全部被阻塞时，新任务就会开始堆积。当任务队列（有界）满后，就会触发拒绝策略A（如丢弃或报错），保护系统不被撑爆。

`publishiOn` 与线程切换：通过`publishiOn` 可以解决上下游阻塞问题。数据流执行到该方法时，会将结果丢入新的调度器的任务队列，由空闲的业务线程抢占执行，实现了接收线程与处理线程的物理隔离。

并发的本质：并发不仅仅是同时执行，其核心本质时多线程同时访问共享的可变状态。

## 2026.11.2 配置库化

### 为什么改

原来是两套真相源：`devices.yml` 定义设备，启动时 `ThresholdLoader` 再读 `point` 表把阈值覆盖到 yml 对象上。问题在于——加一台设备要改文件重启；库里新增的测点阈值覆盖不到；改阈值还得靠"启动时覆盖"这种一次性动作。

结论：库是唯一真相源，启动直接把设备、测点、阈值一次读进内存。

### 删了什么

| 删除物 | 原因 |
|---|---|
| `devices.yml` + `spring.config.import` | 配置改由库提供，文件不再参与 |
| `ThresholdLoader` | 阈值不再是"覆盖"，改为加载时一并读出 |
| `DeviceConfigRunner` | 它的职责只是启动打印验证，加载日志已能替代 |
| `InMemoryPointStore` + 三处 `@ConditionalOnProperty` + `donghuan.store.type` | 已有 Jdbc 实现，双实现是早期调试遗留 |

### 加载怎么做的

一条 SQL 把设备和测点拉平：`device left join point on p.device_id = d.id and p.enabled = 1`，两边都带 `d.enabled = 1`。

用 `RowCallbackHandler` 逐行聚合，不用 `RowMapper`：结果集是 device × point 的展开行，同一台设备会出现多次，需要自己按 `device_code` 归并——第一次遇到就 new 一个 `DeviceConfig` 放进 map，之后只往里 append `Point`。测点为空的行靠 left join 保留，`point_code` 为 null 直接跳过。

**`p.enabled = 1` 必须写在 `on` 里，不能放 `where`。** 放 where 会让 left join 退化成 inner join，测点全被禁用的设备整台消失。

### 为什么是 volatile Map + unmodifiableMap

结构选型上比较过四种：

| 方案 | 否掉的原因 |
|---|---|
| `ConcurrentHashMap` | 逐个 `put` 有半成品窗口，`findDevice` 可能读到"设备在、测点只加了一半"；遍历无序 |
| `Map.copyOf` | 不保序，等价于 HashMap 语义，设备列表顺序每次重启都变 |
| `CopyOnWriteArrayList` | 没有并发修改场景，且 `findDevice` 退化成线性查找 |
| `volatile Map` + `LinkedHashMap` + `Collections.unmodifiableMap` | 采用 |

用 `LinkedHashMap` 构建完再 `Collections.unmodifiableMap` 包一层做**整体替换**，形成 copy-on-write 快照：读线程要么看到旧快照、要么看到新快照，不会看到中间态；`volatile` 负责引用的安全发布，`unmodifiable` 保证发布后内容不再被改。配置是读多写极少，这个代价最划算。

### 语义变化（要记住的代价）

以前库里 `min_value / max_value` 为 NULL 时，回退到 yml 里的默认值；现在没有回退，NULL 就是"没配阈值"，`ThresholdChecker` 里 `min/max` 判空后跳过判断。

所以种子数据必须把 18/38、30/70 这些阈值真的写进库，否则越限永远不触发。

`AlarmService` 的 `@Order(3)` 不能跟着 `ThresholdLoader` 一起删：告警回填仍要早于 `AcquisitionService`，否则 MQTT retained 消息先到、回填后置，同一测点会出现两条 ACTIVE。

### 踩坑

1. `rs.getString("deviceCode")` —— 库列名是 `device_code`，写成驼峰直接 `Column not found`。所有列名都按库里的下划线写法。
2. `Collections<DeviceConfig> getDevices()` 编译不过 —— `Collections` 是工具类不能带泛型，应为 `Collection<DeviceConfig>`。
3. 取阈值用 `getBigDecimal` 不用 `getDouble` —— `getDouble` 把 NULL 变成 0，就分不清"没配"和"配了 0"。
4. `computeIfAbsent` 用不了 —— 方法引用里有检查异常，`throws SQLException` 的 lambda 塞不进去，只能手写 `if (device == null) { ... }`。

### 验证

启动日志链路：`载入设备配置{th-01=...}` → `点位映射加载2条` → `√ MQTT连接成功` → `设备接入完成`。

### 遗留

- 读库在 `common` 包、写库计划放 `store` 包，包职责不一致。
- 空表时只打 debug，没有 warn，"启动无设备"容易被当成正常。
- 后面做设备 CRUD 时，写完库必须重载这份快照，否则内存和库不一致。

合作社（平台）→ 种植户（租户）→ 大棚（device）→ 测点（point）

一句话链路：选购套餐 → 订购 → 管理员审批 → 开通任务 → 运维绑定设备/生成测点 → 数据上报 → 租户可见 → 越限告警 → 确认 → 报修工单。

**今天定的几件事**

| 决策 | 结论 | 代价 |
|---|---|---|
| 隔离方式 | 单库 + `tenant_id`，不做独立 schema | 每个查询都要记得带条件，漏一处就是越权 |
| 越权返回 | 统一 404 | 不泄露资源存在性，但排障时分不清"没有"和"无权" |
| 平台账号 | `user.tenant_id` 为空 | SQL 要分"平台看全部"和"租户看自己"两支 |
| 表分期 | 一期只加 `tenant` 表 + `user`/`device` 的 `tenant_id` | 套餐、工单放到二、三期，避免一期就背十几张表 |
| 逻辑删除 | 设备、测点、账号都只置 `enabled=0` | 外键与审计链不破，但 `device_code` 删了还占唯一键，恢复只能"编辑 + 启用" |
| 支付 | 只做模拟支付状态 | 不接真实通道，论文里写明是演示 |

**为什么开通流程不能省**

设备总得有个来源。直接给种植户加设备，系统里就没有"买过什么、什么时候开通"的记录；有了套餐—订购—开通，设备能追到 `subscription_id`，限额校验也有依据：超卖在开通时拒绝，而不是事后才发现。

**开发路线重排**

M1 租户化监测平台 → M2 可售卖可开通 → M3 运维与分析 → M4 交付。

阶段 1 是硬前置：没有租户，后面所有页面和接口都要返工。所以下一步只做租户线：`tenant` 表、`user`/`device` 加 `tenant_id`、Session 登录、现有 7 个查询接口全部加过滤。

**风险**

租户过滤漏接口是最大的坑，尤其 `/api/snapshots` 返回全量快照，最容易忘。每个里程碑都要回归一次双租户交叉访问。

**今天没写代码**，只把需求文档和开发路线从机房动环改到合作社场景。之前是"有功能没目标"，现在是"有目标，功能分期挂上去"。

### 一、MqttProtocolAdapter：重连风暴

**问题源码**

```java
if (existing != null && existing.isConnected()) {
    return;
}
```

原逻辑只判定「存在且连接」，漏掉了「存在但未连接」；新 client 上线会被 broker 踢掉旧 client，旧的自动重连又踢掉新的，无限循环。

```bash
旧 client(未连接, 自动重连中) 
  → 新 client 上线 
  → broker 踢旧的 
  → 旧的自动重连 
  → broker 踢新的 
  → 无限循环 + 旧对象泄漏
```

**修改后**

```java
if (existing != null && existing.isConnected()) {
    return;
}
if (existing != null) {
    disconnect(deviceId);
}
```

加存在且未连接情况，断开当前客户端

### 二、登录与会话

失败路径（缺字段 400 / 账号密码错 401）**不创建 session**。

#### AuthController（入口）

```java
@RestController
@RequestMapping("/api/auth")
@RequiredArgsConstructor
public class AuthController {

    public static final String SESSION_KEY = "LOGIN_USER";
    private final AuthService authService;

    public record LoginRequest(String username, String password) {}

    @PostMapping("/login")
    public ResponseEntity<?> login(@RequestBody LoginRequest req, HttpServletRequest request) {
        try {
            LoginUser user = authService.login(req.username(), req.password());
            // 登录成功后才创建会话，失败请求不再产生空 session
            HttpSession session = request.getSession(true);
            // 更换会话 ID，防止会话固定攻击
            request.changeSessionId();
            session.setAttribute(SESSION_KEY, user);
            return ResponseEntity.ok(user);
        } catch (AuthService.InvalidCredentialsException e) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                    .body(Map.of("error", e.getMessage()));
        } catch (IllegalArgumentException e) {
            return ResponseEntity.badRequest()
                    .body(Map.of("error", e.getMessage()));
        }
    }

    @GetMapping("/me")
    public ResponseEntity<?> me(HttpServletRequest request) {
        HttpSession session = request.getSession(false);
        LoginUser user = session == null ? null : (LoginUser) session.getAttribute(SESSION_KEY);
        if (user == null) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                    .body(Map.of("error", "未登录"));
        }
        return ResponseEntity.ok(user);
    }

    @PostMapping("/logout")
    public ResponseEntity<?> logout(HttpServletRequest request) {
        HttpSession session = request.getSession(false);
        if (session != null) {
            session.invalidate();
        }
        return ResponseEntity.ok(Map.of("message", "已退出登录"));
    }
}
```

要点：

- `@RestController` = `@Controller` + `@ResponseBody`，返回值交给消息转换器变 JSON，不当视图名解析。
- `@RequiredArgsConstructor` 给 final 字段生成构造器；单构造器的 Bean 不用写 `@Autowired`。
- `record LoginRequest` 天然不可变 DTO，Jackson 按组件名匹配 JSON，**缺字段就是 `null`**。
- `@RequestBody` 把整个请求体交给 Jackson；body 为空或格式错会先抛 `HttpMessageNotReadableException`，进不了方法体。
- 登录成功后才 `getSession(true)`：失败请求不建 session，避免被刷内存。
- `changeSessionId()` 换 id 防会话固定；必须先 `getSession(true)`，否则当前无会话时抛 `IllegalStateException`。
- `/me`、`/logout` 用 `getSession(false)`，没有会话返回 null 而不是新建。
- 存 `LoginUser` 不存 `UserRow`，物理上不让 `password_hash` 进 session。

#### AuthService（校验）

```java
public LoginUser login(String username, String password) {
    if (username == null || username.isBlank() || password == null || password.isEmpty()) {
        throw new IllegalArgumentException("用户名或密码不能为空");
    }
    UserRow row = userStore.findEnabledByUsername(username).orElse(null);

    // 用户不存在也执行一次哈希比对，避免响应时间差泄露账号是否存在
    String hash = row != null ? row.passwordHash() : DUMMY_HASH;
    boolean matched = passwordEncoder.matches(password, hash);
    if (row == null || !matched) {
        throw new InvalidCredentialsException("用户名或密码错误");
    }
    return new LoginUser(row.id(), row.username(), row.role(), row.tenantId());
}
```

要点：

- 短路求值：`null` 判断必须写在可能 NPE 的调用前面，否则 `null.isEmpty()` 直接炸。
- 用户不存在也跑一次假 hash，两条路径耗时接近 → 防**时序攻击**枚举账号。
- 假 hash 必须是合法 bcrypt（60 位），否则 `matches` 直接返回 false 不做运算，时间对齐白做。
- BCrypt 不能解密，验证是「用哈希串里的盐再算一次」；盐随机且编码在结果里；cost=10 即 2¹⁰ 轮，故意慢。
- `InvalidCredentialsException` → 401，故意不区分"用户不存在"和"密码错"；`IllegalArgumentException` → 400。

#### JdbcUserStore（查库）

```java
private static final String SQL =
        "select id, username, password_hash, role, tenant_id " +
        "from user where username = ? and enabled = 1";

public Optional<UserRow> findEnabledByUsername(String username) {
    List<UserRow> rows = jdbcTemplate.query(SQL, (rs, i) -> {
        long tenant = rs.getLong("tenant_id");
        Long tenantId = rs.wasNull() ? null : tenant;
        return new UserRow(rs.getLong("id"), rs.getString("username"),
                rs.getString("password_hash"), rs.getString("role"), tenantId);
    }, username);
    return rows.stream().findFirst();
}
```

要点：

- `?` 占位符 → `PreparedStatement`，参数走独立通道不参与语法解析，防 SQL 注入。
- `getLong` 遇 NULL 返回 0，`wasNull()` 必须紧挨着该次读取；否则平台账号的 `tenant_id=null` 会变成 0，租户过滤全错。
- `query` + `stream().findFirst()` 返回 Optional；`queryForObject` 空结果会抛 `EmptyResultDataAccessException`，要额外 try/catch。

#### AuthConfig（BCrypt Bean）

```java
@Configuration
public class AuthConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

只引 `spring-security-crypto`，不引 `spring-boot-starter-security`：后者会带来过滤器链拦截所有请求、启动打印随机密码、还要写一堆放行配置。这里只要一个哈希工具类。

#### application.properties（会话）

```properties
server.servlet.session.timeout=30m
server.servlet.session.cookie.name=DH_SESSION
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.same-site=lax
```

`timeout` 是**空闲**超时不是登录时长，持续操作会续期；`http-only` 让 JS 读不到；`same-site=lax` 让跨站 POST 不带 cookie，挡大部分 CSRF；改名少暴露技术栈。

#### 完整链路

```
POST /api/auth/login {"username","password"}
→ DispatcherServlet 路由 → Jackson 反序列化成 LoginRequest
→ AuthService 非空校验 → JdbcUserStore 查 user
→ BCrypt.matches → 成功则 LoginUser
→ getSession(true) → changeSessionId() → setAttribute("LOGIN_USER")
→ 200 + Set-Cookie: DH_SESSION
```

#### 踩坑

1. `password.isEmpty()` 拦不住 `null`。`null.isEmpty()` 直接 NPE，`||` 短路救不了它，因为 `password` 那半段没有 null 判断。修法：`password == null || password.isEmpty()`。
2. 方法参数写 `HttpSession session` 会强制 `getSession(true)`，**登录失败也建 session**。改成 `HttpServletRequest` + 成功后取 session。
3. 登录成功后不 `changeSessionId()` 就有会话固定风险，手写 session 时 Spring 不会帮你做。
4. 三目里 `session.getAttribute` 前必须先判 session 为 null，否则未登录访问 `/me` 直接 NPE。

#### 边界（没做但要知道）

- `username` 排序规则 `utf8mb4_0900_ai_ci` 大小写不敏感，`Farmer1` 能登 `farmer1`。
- BCrypt 只取前 72 字节，密码长度没上限校验。
- 没有登录失败次数限制。
- session 在 Tomcat 堆内存里，重启全掉线，不是"持久化"。
- `SESSION_KEY` 已移到 `AuthConstants`，见下。
- `role` 已改枚举，见下。

#### AuthInterceptor（新增）

```java
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
    HttpSession session = request.getSession(false);
    LoginUser user = session == null ? null : (LoginUser) session.getAttribute(AuthConstants.SESSION_KEY);

    if (user == null) {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"error\":\"未登录\"}");
        return false;
    }

    request.setAttribute(AuthConstants.REQUEST_USER, user);   // 供 @RequestAttribute 取

    String path = request.getRequestURI().substring(request.getContextPath().length());
    if ("GET".equals(request.getMethod())) return true;

    String perm = requiredPermission(request.getMethod(), path);
    if (perm == null || !allowed(perm, user.getRole())) {
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"error\":\"无权限\"}");
        return false;
    }
    return true;
}
```

- 返回 `false` 前必须自己把响应写完（状态码 + 内容），Spring 不会补；只 `return false` 会得到一个空白 200。
- 三条拒绝路径：未登录 401、规则缺失 403、角色不符 403。
- **fail-closed**：写请求没配规则一律拒绝。原来写的是 `return true`（fail-open），漏一条规则就是越权入口。
- `getSession(false)` 不新建会话；登录请求被 `excludePathPatterns` 排除。
- 路径用 `URI - contextPath` 截取，不能直接用 `getRequestURI()`，否则带上下文路径时匹配不上。
- 登录校验通过后 `request.setAttribute`，Controller 用 `@RequestAttribute` 取当前用户，不用每个 Controller 重复解析 session。

### 新增/修改文件

#### LatestValueStore（修改）

- `findAllSnapshots()` → `findAllSnapshots(TenantScope scope)`。
- 写侧 `snapshot(PointValue)` 不加 scope：采集链路永远全量写入，权限只影响读。

#### PointSnapshot（修改）

- 注入 `DeviceProperties`，按 `deviceCode` 反查设备 `tenantId`，再交给 `scope.canSee`。
- 设备被停用/删除后配置表里查不到，旧快照 key 必须过滤掉；写成 `.get()` 会抛 `NoSuchElementException`，一个残留 key 能让所有请求 500。
- 最终形态：

```java
@Override
public Map<String, PointValue> findAllSnapshots(TenantScope scope) {
    Map<String, PointValue> result = new HashMap<>();
    if (scope.seeAll()) return Map.copyOf(latestSnapshot);
    latestSnapshot.forEach((key, value) -> {
        if (deviceProperties.findDevice(value.getDeviceCode())
                .map(d -> scope.canSee(d.getTenantId()))
                .orElse(false)) {
            result.put(key, value);
        }
    });
    return result;
}
```

- `Map.copyOf` 只留在 `seeAll` 分支：这分支返回全量，必须给调用方一个副本，避免外部拿到内部 map；过滤分支本来就在往新 `HashMap` 里塞，再拷一次是多余分配。
- 遍历 `ConcurrentHashMap` 不需要先 copy：迭代器弱一致，并发写最多看到部分新值，不会抛 `ConcurrentModificationException`。

#### SnapshotService（新增）

- 薄转发：`LoginUser` → `TenantScope.of(user)` → `snapshot.findAllSnapshots(scope)`。
- 不抛 404：集合查询的空结果是合法状态（应用刚启动、租户名下没设备），返回 `200 {}`。404 只给路径里带唯一资源的接口。

#### SnapshotController（修改）

- 改为注入 `SnapshotService`，方法加 `@RequestAttribute(AuthConstants.REQUEST_USER) LoginUser user`。
- 删掉原来的 `PointSnapshot` 字段与 import，Controller 不直接依赖 Store。

#### ModbusTcpClient（新增）

极简 Modbus TCP 主站，只用 JDK `Socket`，不引第三方库；一次读请求 = MBAP 头（7 字节）+ PDU，支持 FC1/2/3/4。校验事务标识、协议标识、单元标识、功能码和字节数，从站异常响应（功能码最高位置 1）抛 `ModbusException` 并带异常码文案；地址上限 `0xFFFF`，一次最多读 2000 位 / 125 个字。连接复用，连接/读超时各 3s，读超时或 IO 异常由调用方 `close`，下一轮重建。

```java
public synchronized int[] read(RegisterType type, int address, int quantity) throws IOException {
    ensureConnected();

    int fc = type.functionCode();
    int tid = nextTransactionId();

    // 请求：MBAP 头 + PDU
    ByteBuffer req = ByteBuffer.allocate(12);
    req.putShort((short) tid);      // 事务标识
    req.putShort((short) 0);        // 协议标识，Modbus 固定 0
    req.putShort((short) 6);        // 后续长度：unitId + PDU
    req.put((byte) unitId);
    req.put((byte) fc);
    req.putShort((short) address);
    req.putShort((short) quantity);

    out.write(req.array());
    out.flush();

    // 响应：先收 7 字节 MBAP，再按长度字段收 PDU
    ByteBuffer header = ByteBuffer.wrap(readFully(7));
    int respTid = header.getShort() & 0xFFFF;
    int respProtocol = header.getShort() & 0xFFFF;
    int respLength = header.getShort() & 0xFFFF;
    int respUnitId = header.get() & 0xFF;

    if (respTid != tid) {
        throw new IOException("事务标识不匹配：" + tid + " / " + respTid);
    }
    if (respProtocol != 0) {
        throw new IOException("协议标识非 0: " + respProtocol);
    }
    if (respUnitId != unitId) {
        throw new IOException("单元标识不匹配：" + unitId + " / " + respUnitId);
    }

    byte[] pdu = readFully(respLength - 1);
    int respFc = pdu[0] & 0xFF;

    // 异常响应：功能码最高位置 1，第二字节是异常码
    if (respFc == (fc | 0x80)) {
        int code = pdu.length > 1 ? pdu[1] & 0xFF : -1;
        throw new ModbusException(code, "Modbus 异常响应：fc=" + fc + "，异常码=" + code);
    }
    if (respFc != fc) {
        throw new IOException("功能码不匹配：" + fc + " / " + respFc);
    }

    if (type.isBit()) {
        int[] bits = new int[quantity];
        for (int i = 0; i < quantity; i++) {
            bits[i] = ((pdu[2 + i / 8] & 0xFF) >> (i % 8)) & 0x01;
        }
        return bits;
    }

    int[] words = new int[quantity];
    for (int i = 0; i < quantity; i++) {
        words[i] = ((pdu[2 + i * 2] & 0xFF) << 8) | (pdu[3 + i * 2] & 0xFF);
    }
    return words;
}
```

#### ModbusPoller（新增）

单设备一轮轮询：位类型读 1 位，字类型按 `dataType.registerCount()` 读 1/2 个寄存器；单测点异常码只跳过该测点，连接级 IO 异常关闭连接并结束本轮，下一轮自动重连。一轮结果组装成 `{pointCode:[寄存器值]}` JSON 进流，适配器不解码。

```java
public void poll() {
    Map<String, int[]> snapshot = new LinkedHashMap<>();
    boolean linkBroken = false;

    for (DeviceConfig.Point point : device.getPoints()) {
        try {
            int quantity = point.getRegisterType().isBit()
                    ? 1
                    : point.getDataType().registerCount();
            int[] words = client.read(point.getRegisterType(), point.getAddress(), quantity);
            snapshot.put(point.getPointCode(), words);

        } catch (ModbusTcpClient.ModbusException e) {
            // 从站回了异常码，链路是通的，只跳过这个测点
            log.warn("Modbus 读取异常：deviceCode={}，pointCode={}，{}",
                    device.getDeviceCode(), point.getPointCode(), e.getMessage());
        } catch (IOException e) {
            // 连接级失败：关掉连接，下一轮 ensureConnected 自动重连
            client.close();
            linkBroken = true;
            break;
        }
    }

    if (linkBroken || snapshot.isEmpty()) {
        return;
    }

    try {
        RawMessage raw = new RawMessage();
        raw.setDeviceCode(device.getDeviceCode());
        raw.setProtocol(Protocol.MODBUS);
        // 原始寄存器值以 JSON 进流：{"temperature":[16256,0], ...}
        raw.setPayload(objectMapper.writeValueAsString(snapshot));
        raw.setReceivedAt(Instant.now());
        messageStream.emit(raw);
    } catch (Exception e) {
        log.warn("Modbus 报文组装失败：deviceCode={}", device.getDeviceCode(), e);
    }
}
```

#### ModbusProtocolAdapter（新增）

每设备一个 `ModbusTcpClient` + `ModbusPoller`，任务存 `ConcurrentHashMap`，共享 `ScheduledExecutorService`（默认 4 线程）；周期取该设备测点最小 `freq`，下限 1s，缺省 5s。`resolvePoints` 回填解析字段，并用 `removeIf` 剔除无效测点，保住 `CopyOnWriteArrayList` 实例。

```java
// connect(DeviceConfig device)
ModbusEndpoint endpoint = ModbusEndpoint.parse(device.getConnection().getConfig());
if (!resolvePoints(device)) {
    return;
}

ModbusTcpClient client = new ModbusTcpClient(endpoint.host(), endpoint.port(), endpoint.unitId());
ModbusPoller poller = new ModbusPoller(device, client, messageStream, objectMapper);
int period = pollPeriod(device);

ScheduledFuture<?> future = scheduler.scheduleWithFixedDelay(
        poller::poll, 1, period, TimeUnit.SECONDS);

tasks.put(device.getDeviceCode(), new DeviceTask(client, future));

// resolvePoints(DeviceConfig device)：解析测点地址并回填解析字段，无效测点剔除；全部无效则跳过设备
List<DeviceConfig.Point> valid = new ArrayList<>();
for (DeviceConfig.Point point : device.getPoints()) {
    try {
        ModbusPointSpec spec = ModbusPointSpec.parse(
                point.getAddressText(), point.getDataTypeCode());
        point.setRegisterType(spec.registerType());
        point.setAddress(spec.address());
        point.setDataType(spec.dataType());
        point.setScale(spec.scale());
        valid.add(point);
    } catch (IllegalArgumentException e) {
        log.warn("Modbus 测点配置无效，已跳过：deviceCode={}，pointCode={}",
                device.getDeviceCode(), point.getPointCode());
    }
}
if (valid.isEmpty()) {
    return false;
}
// 在原列表剔除，保住 CopyOnWriteArrayList 实例
device.getPoints().removeIf(point -> !valid.contains(point));
return true;
```

#### ModbusDataType（新增）

```java
public double decode(int[] words) {
    return switch (this) {
        case BOOL -> words[0] == 0 ? 0D : 1D;
        case UINT16 -> words[0] & 0xFFFF;
        case INT16 -> (short) words[0];
        case UINT32 -> ((long) (words[0] & 0xFFFF) << 16) | (words[1] & 0xFFFF);
        case INT32 -> ((words[0] & 0xFFFF) << 16) | (words[1] & 0xFFFF);
        case FLOAT32 -> Float.intBitsToFloat(
                ((words[0] & 0xFFFF) << 16) | (words[1] & 0xFFFF));
    };
}
```

### 决策记录

| 决策 | 结论 | 代价 |
|---|---|---|
| 配置刷新方式 | 不做 `reload()`，写库成功后直接操作内存列表 | 避免重建对象后 poller 仍持有旧引用、解析字段丢失；`findDevice` 变 O(n) |
| 并发容器 | 直接用 JDK `CopyOnWriteArrayList`，不自造 copy | 遍历拿旧快照，add/remove 不抛 CME；浅层保护，元素内部字段仍需原地更新 |
| 测点运行时生效 | Service 解析并填好 `registerType/address/dataType/scale`，poller 下一轮直接读 | 新增/改地址立即生效；协议、连接串变更仍未热生效（7-3） |
| 设备删除顺序 | 先逻辑删 `device` + `point`，再 `disconnect`，最后移出内存 | 断开异常只记日志，不影响库与内存一致性 |
| 测点删除 | `removeIf` + `refCache.refresh()` | 采集与 `point_id` 映射同步失效，不会残留映射 |
| Modbus 主站 | 不引第三方库，JDK `Socket` 手写 MBAP + PDU | 少一个依赖、报文全可控；代价是只实现读，异常码和字节数都要自己校验 |
| 解码位置 | 适配器只读寄存器，原始值 JSON 进流，解析层解码 | 与 MQTT 链路统一，解析器按协议分发；`RawMessage` 比真实值大 |
| 连接与任务 | 每设备独立 client + 轮询任务，共享线程池 | 一台设备断线不影响其他设备；线程池默认 4，设备再多要调 `modbus.pool-size` |
| 轮询周期 | 取该设备测点最小 `freq`，下限 1s | 不同采样周期的测点只能按最快的一起读，暂不支持按测点分任务 |

### 踩坑：主题热切换后新旧主题交替出数

- 现象：`PUT /api/devices/t-hot` 把 topic 从 `donghuan/test/hot` 改成 `donghuan/test/hot2`，`latest` 在 20/30 之间交替，库里也是 `20,30,20,30...`。
- 根因：Paho clientId 固定为 `donghuan_java_{deviceCode}`，`cleanSession=false` 时 broker 保留旧会话和旧订阅；新连接恢复旧会话后 `connectComplete` 又订阅新主题，于是两个主题都在收。
- 改法：`cleanSession=true`，每次连接都是干净会话，订阅只由 `connectComplete` 建立。
- 代价：断线期间 QoS1 的消息不补发（原 `cleanSession=false` 会补）。设备按秒上报，丢几秒可接受；要补发就得保持固定 clientId + `cleanSession=false`，并在切主题时先 `unsubscribe` 旧主题。

```java
// 按测点配置的采集周期判断本轮是否读取；未配置则每轮都读
private boolean due(DeviceConfig.Point point, Instant now) {
    Integer freq = point.getFreq();
    if (freq == null || freq <= 0) {
        return true;
    }
    Instant last = lastRead.get(point.getPointCode());
    return last == null || Duration.between(last, now).getSeconds() >= freq;
}
```

```java

        disconnect(deviceCode);
        return;

        ScheduledFuture<?> future = scheduler.scheduleWithFixedDelay(
                existing.poller()::poll, period, period, TimeUnit.SECONDS);
        tasks.put(deviceCode,
                new DeviceTask(existing.client(), existing.poller(), future, period));
```

```java
// 解析测点地址并回填；无效测点保留在内存并标记，供页面查看和后续编辑修复
private boolean resolvePoints(DeviceConfig device) {
    boolean anyValid = false;

    for (DeviceConfig.Point point : device.getPoints()) {
        // 已解析的有效测点直接保留，避免轮询线程读到半更新字段
        if (!point.isInvalid() && point.getRegisterType() != null) {
            anyValid = true;
            continue;
        }
        try {
            ModbusPointSpec spec = ModbusPointSpec.parse(
                    point.getAddressText(), point.getDataTypeCode());

            point.setRegisterType(spec.registerType());
            point.setAddress(spec.address());
            point.setDataType(spec.dataType());
            point.setScale(spec.scale());
            point.setInvalid(false);
            anyValid = true;
        } catch (IllegalArgumentException e) {
            point.setInvalid(true);
            log.warn("Modbus 测点配置无效，已跳过：deviceCode={}，pointCode={}，address={}，原因={}",
                    device.getDeviceCode(), point.getPointCode(),
                    point.getAddressText(), e.getMessage());
        }
    }

    if (!anyValid) {
        log.warn("Modbus 设备没有有效测点，跳过设备：deviceCode={}", device.getDeviceCode());
        return false;
    }
    return true;
}
```

### 后端关键逻辑

- **服务项保存**：一个事务内更新 `service_item`，指标模板先删后插；编码唯一冲突返回 409；更新不传 `enabled` 时保留原状态
- **提交申请**：租户从 Session 用户取，不信任前端；申请单号 `SAyyyyMMddNNNN`；初始 `PENDING`；大棚数必须 1~服务项上限
- **审批通过**：只允许 `PENDING`；同一事务内把申请置 `APPROVED` 并插入 `provision_task`；`uk_provision_application` 防重复审批
- **驳回**：`reason` 必填且 ≤255，申请置 `REJECTED`，种植户端可见原因
- **执行开通**：
  - 事务内校验任务状态与申请状态；大棚数不能超过服务项上限，每棚测点数不能超过上限
  - 新设备按 `device_code` 插入并绑定租户；已有启用设备直接绑定租户，不重复生成
  - 测点按指标模板生成：编码/名称/单位/阈值/量程/周期，地址由运维填写；已存在的测点跳过
  - 申请置 `PROVISIONED`、任务置 `DONE`、写 `provision_task_device` 快照
  - 事务提交后刷新配置快照并触发适配器连接，打印一条可观测日志
- **历史任务详情**：读 `provision_task_device`，不实时联设备表；设备后续复用/改名不影响历史记录

### review 后修的 5 个问题

1. 开通协议与已有设备不一致 → 409，不静默改协议
2. 逻辑删除的模板测点 → 开通时恢复 `enabled=1` 并计入单棚上限
3. 更新服务项不传 `enabled` → 保留原状态，避免默认值意外启用

### 踩坑

- **运行目录不是源码目录**：应用从 `target/classes/static` 提供页面，改 `src/main/resources/static` 后必须同步/重新构建才生效；本次直接同步到运行目录，未重启 8080

### 就业视角

- **功能权限 + 数据权限**：拦截器管“能不能调”，Store 的 `tenant_id` 管“能看哪些行”，两层缺一不可

- **快照模式**：订单/任务类历史数据不实时联主表，避免主数据被改后历史失真
- **事务边界**：审批生成任务、开通生成设备/测点/快照都放在同一事务；通知与刷新配置放到提交后
- **前后端权限分工**：前端隐藏入口只是体验，后端 403/404 才是安全边界

## 知识点

1. 【八股】枚举 ：
2. 【八股】面向接口编程：接口只暴露状态机需要动作，不暴露sql细节，项目中体现：AlarmService依赖AlarmStore,换实现业务代码不动
3. 【八股】：@RequiredArgsConstructor用于自动生成包含必需参数的构造函数。必需参数是指那些被声明为 *final* 或者有 *@NonNull* 注解的成员变量
4. 【八股】：`volatile` 的可见性 + 不可变对象安全发布
5. 【八股】：`@PostConstruct` 的执行时机（依赖注入之后、Bean 可用之前）
6. *@RestController*是一个组合注解，它结合了*@Controller*和*@ResponseBody*注解的功能，使得在使用*@RestController*标记的类中，每个方法的返回值都会以JSON或XML的形式直接写入HTTP响应体中
7. `record` 与普通类的区别（值语义、不可变、紧凑构造器）
8. `Optional` 用来表达「查不到 / 无法判定」，不要用 null 或魔法值
9. 无状态组件（纯函数）更容易测试和复用
10. `JdbcTemplate` 三种回调：`RowCallbackHandler` （逐行、void）vs`RowMapper` （逐行、返回对象并收集成 List）vs`ResultSetExtractor` （整个 `ResultSet` 自己循环）
11. lambda 的变量捕获规则（effectively final）
12. Reactor 热流（`Sinks.Many` ）与冷操作符的区别
13. `ErrorCallbackNotImplemented` 这个名字的含义：Reactor 检测到「你没有实现错误回调」
14. 【八股】Session 与 Cookie：cookie 只带 sessionId，数据在服务端内存；`getSession(true)` 没有就建，`getSession(false)` 没有返回 null；`changeSessionId()` 是会话固定攻击的标准防护。
15. 【八股】BCrypt 不能解密，验证是「用哈希串里的盐再算一次」；盐随机且编码在结果里，所以同密码每次结果不同；cost 决定运算轮数，故意慢。正因为慢，才有**时序攻击**（靠响应耗时判断用户名是否存在），解法是给不存在的用户也跑一次哈希。
16. 【八股】`PreparedStatement` 防注入的本质：参数走独立通道，不参与 SQL 语法解析，所以引号、分号都只是普通字符。
17. 【八股】`ResultSet.getLong` 遇到 NULL 返回 0，与真实的 0 无法区分；`wasNull()` 用来问「刚才那次读取是不是 NULL」，必须紧挨着该读取调用。
18. 【八股】功能权限 vs 数据权限：前者管「能不能调这个接口」（拦截器按角色校验），后者管「能查到哪些行」（Store 里的 `tenant_id` 条件）。只做前者会出现「接口放行、数据串租户」。项目中对应 `AuthInterceptor` 和 `TenantScope`。
19. 【八股】`ConcurrentHashMap` 的迭代器是**弱一致**的：遍历时允许并发写，不抛 `ConcurrentModificationException`，最多看到部分新值；要某一时刻的精确视图才需要先拷贝。
20. 【八股】`Map.copyOf` 是防御性拷贝：返回真正不可变的副本，改它抛 `UnsupportedOperationException`，原 map 有 null 键值则直接 `NPE`。把内部集合交给外部时必须给副本或不可变视图。
21. 【八股】`Optional.get()` 等于又把「可能没有」变回异常，应使用 `map(...).orElse(...)` 或 `orElseThrow(...)`；项目里内存快照的旧 key 一旦查不到设备，`get()` 会让所有请求 500。
22. 【八股】HTTP 状态码边界：未登录 401、已登录但角色不够 403、数据权限越权统一 404（不泄露存在性）、集合空结果 200 + 空集合、415 是 Content-Type 不支持（在进方法前就被拒绝），不要和参数错误 400 混用。
23. 【八股】MySQL `character_set` 管字节怎么存，`collation` 管怎么比较排序（`utf8mb4_0900_ai_ci` 的 `ci` 不区分大小写）；MySQL 的 `utf8` 最多 3 字节存不了 emoji，所以用 `utf8mb4`。双重编码看 HEX：`E6B8A9` 是「温」，`C3A6C2B8...` 说明 UTF-8 被当 latin1 又编码了一次。

## 模块描述

*接入解析* ：适配器按配置接入设备配置目前来自`devices.yml`找不到设备时这条报文不产出值；收到报文payload后装入`RawMessage`，再把`rw` `emit`进程内发布—订阅流，在流中`parser`遍历测点，每个测点调用两次`extract`抽取数值和`ts`，目前任意值为空就`continue`；`parser`再把值装入`PointValue`返回`List<PointValue>`；流用`flatMapIterable`拆成单个值，再`share()`供下游存储和警告两路订阅

*警告收敛* ：系统初始化时从 alarm 表加载 active 到内存，警告模块从流中获取数据后先进行阈值判定；阈值存在内存中，也是系统启动时从 point 表中读取阈值到内存覆盖到yml配置的对象上，目前如果库里新增配置文件没有的测点，阈值不会被加载；先由 deviceId 和 pointId 映射为内部键point_id；判定结果返回是否越限（布尔）、阈值类型、当前阈值，按内部键在内存中查找 active警告。若无同测点的 active 警告就 insert，若有 active 警告就更新数值保留首次警告时间；恢复正常值就将 status=recovered，再从内存中移除。 
 边界：设备离线后保留警告，重新上线后按新报文重新判定：仍越限则更新同一条告警的数值，恢复正常则置为RECOVERED；警告测点阈值被修改，收到的报文根据修改后的阈值判定，若恢复正常则 recovered。若内存未加载到 active，下条警告来时会 insert，同一测点多条 active 警告收敛失效。所以启动回填失效不能静默，要启动失败或降级打标记。
