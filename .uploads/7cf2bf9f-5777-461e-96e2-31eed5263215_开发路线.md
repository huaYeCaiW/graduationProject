# 农业大棚监测与合作社服务平台 — 开发路线（v3）

## 0. 现在只做一件事

**阶段 1：把"租户"这条线打通。** 加 `tenant` 表、给 `user` / `device` 加 `tenant_id`、做 Session 登录、让现有 4 个查询接口全部按租户过滤。

做完这一件事，系统才从"一个机房 demo"变成"能给种植户用的平台"。其余都是在这条线之上叠加。

| 层 | 选型 |

## 3. 里程碑

**推进原则：** 每个里程碑停下验收，闸门未过不进入下一段；不裁剪范围，但可以调整顺序。

| 里程碑 | 内容 | 判定 |
|---|---|---|
| M1 租户化的监测平台 | 阶段 0-4 | 两个种植户交叉看不到对方数据；告警可确认；Modbus 数据入链路 |
| M2 可售卖、可开通 | 阶段 5-7 | 下单→审批→开通→新大棚出数据全流程跑通 |
| M3 运维与分析 | 阶段 8-9 | 工单闭环；聚合与趋势接口可用 |
| M4 交付 | 阶段 10 | 三端页面可用；Compose 一键启动；压测与验收留档 |

### M1 闸门

- 两个租户账号分别登录，互查对方大棚返回 404/403
- 高频越限一分钟，`alarm` 表只新增 1 条 ACTIVE；恢复后自动 RECOVERED
- 跨租户的告警确认被拒绝
- Modbus 模拟从站数据与本有 MQTT 数据进入同一条处理链路

### M2 闸门

- 种植户下单 → 管理员审批 → 运维开通 → 种植户端立即可见新大棚
- 超过套餐限额的开通被拒绝
- 逻辑删除设备后历史数据仍在，且可通过"编辑 + 启用"恢复
- 新增大棚只改数据，不改核心代码

### M3 闸门

- 工单从发起到结案状态流转正确，种植户只能看到自己的工单
- 聚合接口按时间粒度输出 min/max/avg
- 趋势接口能判断上升 / 下降 / 平稳

### M4 闸门

- 三端页面均可访问，数据刷新延迟 ≤ 3s
- 干净环境 Compose 一条命令启动
- 7 天前数据被定时任务清理
- 需求文档第 9 节 12 条验收项逐条通过并留记录

## 4. 阶段计划

### 阶段 0：技术债收口（不计入里程碑）

**任务**

- 修 `MqttProtocolAdapter` 的四处遗留（重连、UTF-8、枚举、重订阅）
- `Point.freq` 改 `Integer`
- 清理过时注释与 `README.md` 中的 `store.type`
- `DeviceProperties` 空表 warn

**完成标准**

- 停掉 EMQX 再启动，MQTT 自动重连且重新订阅成功，数据恢复上报
- 编译无警告级遗留注释

### 阶段 1：租户域与登录鉴权（M1 主线）

**任务**

- `tenant` 表：编码、名称、联系人、电话、状态
- `user` 加 `tenant_id`（平台账号为空）；`device` 加 `tenant_id`（默认平台租户）、`subscription_id`
- 种子数据：平台租户、合作社运维账号、两个种植户账号及其大棚
- BCrypt 密码；Session 登录；登录/登出接口
- 拦截器：未登录 401；写接口按角色校验；跨租户 404
- 现有查询接口全部加租户过滤：`/api/devices`、`/api/devices/{id}`、`/api/points/.../latest`、`/api/points/.../range`、`/api/alarms`、`/api/alarms/active`、`/api/snapshots`
- 把 `AlarmController` 里的常量 `TEST_USER_ID` 换成 Session 当前用户

**完成标准**

- 两个种植户账号登录后只能看到自己的设备与数据
- 跨租户改 URL 拿不到数据
- 告警确认记录的是真实登录用户

**决策记录（阶段 1 必写）**

| 决策 | 结论 | 代价 |
|---|---|---|
| 隔离方式 | 单库 + `tenant_id` | 每个查询都要记得加条件，漏一处就是越权 |
| 越权返回码 | 统一 404 | 不泄露资源存在性，但排障时看不出是"没有"还是"无权" |
| 平台账号归属 | `user.tenant_id` 为空 | SQL 里要区分"平台看全部"与"租户看自己"两种分支 |
| 快照接口 | 按用户角色返回不同范围 | 最容易漏租户过滤，必须单独回归 |

### 阶段 2：设备 / 测点 CRUD

**任务**

- `DeviceStore` 接口：`findState` / `insertDevice` / `updateDevice` / `setDeviceEnabled` / `findPointState` / `insertPoint` / `updatePoint` / `setPointEnabled`，实现放 `store/jdbc/JdbcDeviceStore`
- 六个接口：设备增/改/删，测点增/改/删；删除一律逻辑删除
- 写库成功后刷新配置快照（`DeviceProperties` 重载）
- 副作用：改协议用旧配置的适配器断开再按新配置连接；测点级改动只需刷新快照
- 恢复路径：编辑 `enabled=true`，不复用已删除的 `device_code`

**完成标准**

- 前端 `devices.html` 能成功提交一台新大棚及其测点，且无需重启即可采数
- 删除设备后历史数据仍在
- 重复 `device_code` 返回 409

**易错点**

- 不用 `UPDATE` 影响行数判断存在性（驱动默认返回匹配行数，值未变也返回 1）
- 写路径不能查 `PointRefCache`（它只加载 `enabled=1`，新增测点查不到 id）
- `device_code` 逻辑删除后仍占唯一键，不能靠"删了再建同名"恢复

### 阶段 3：Modbus 适配器

**任务**

- 实现 `ProtocolAdapter` 的 Modbus TCP 版本
- pymodbus 模拟从站：水肥灌溉（阀门状态、流量、累计用水）
- 配置声明寄存器地址、数据类型、单位、采样周期

**完成标准**

- MQTT 与 Modbus 两条数据进入同一条处理链路
- 新增 Modbus 设备只改数据

### 阶段 4：租户过滤补全 + 设备在线状态

**任务**

- 逐接口回归租户过滤，重点快照与聚合类接口
- 记录 `last_seen_at`，超时判定离线并在列表展示
- 离线阈值可配置，不做离线告警（本期只在页面展示）

**完成标准**

- M1 闸门全部通过

### 阶段 5：服务套餐与订购

**任务**

- `service_package` 表与维护接口（管理员）
- `subscription` 表；种植户下单接口（套餐、大棚数量、联系方式）
- 模拟支付：下单后置 `pay_status=PAID`，不接真实通道
- 管理员审批接口：通过 / 驳回 + 意见
- 限额校验：订购数量不超过套餐上限

**完成标准**

- 种植户能下单并在"我的订购"看到状态
- 管理员能审批，状态流转正确

### 阶段 6：开通流程

**任务**

- 审批通过生成 `provision_task`
- 运维执行开通：绑定 `device_code` 与协议、按套餐模板生成测点骨架（编码/名称/单位/默认阈值）
- 开通时校验套餐限额（大棚数、每棚测点数）
- 开通完成刷新配置快照，设备自动进入采集
- `device.subscription_id` 记录来源，支持追溯

**完成标准**

- 从下单到出数据全流程无需重启
- 超限开通被拒绝
- 已存在设备可直接绑定租户，不重复生成

### 阶段 7：三端页面

**任务**

- 种植户端：登录、我的大棚、历史曲线、告警、套餐选购、我的订购、报修
- 运维端：总览、设备与测点管理、开通任务、告警处理、工单处理
- 平台后台：租户、套餐、账号、订购审批、运行概览
- 统一页面骨架与请求封装，沿用 `devices.html` 的单文件风格

**完成标准**

- 三端页面数据刷新延迟 ≤ 3s
- 按角色隐藏越权入口，但后端仍强制校验

### 阶段 8：报修工单

**任务**

- `work_order` 表与状态机：待受理 → 处理中 → 已完成 / 已取消
- 种植户发起、运维接单与结案、种植户查看进度
- 工单必须带租户过滤

**完成标准**

- 双账号走通一次完整工单
- 种植户看不到他人工单

### 阶段 9：聚合、趋势与农情日报

**任务**

- SQL 聚合：按时间粒度输出 min / max / avg
- 滑动窗口趋势判断：上升 / 下降 / 平稳
- 农情日报：按天汇总每棚温湿度光照极值均值与告警次数
- REST 接口暴露，页面接聚合结果渲染

**完成标准**

- 历史曲线直接用聚合结果
- 趋势在越限前能给出上升信号
- 日报数据与明细能对得上

### 阶段 10：部署与完整验收

**任务**

- Docker Compose：应用 + MySQL + EMQX + 模拟器
- 每日定时清理 7 天前数据；运维手动清理接口
- 初始化 SQL 与配置样例（含租户、套餐种子数据）
- 压测：并发测点 ≥ 100（目标 500+）、峰值 ≥ 500 条/秒、断线 5s 重连不丢
- 按需求文档第 9 节 12 条逐条验证并留记录

**完成标准**

- 干净环境一条命令启动
- 全部验收项留档

```

                          阶段5 套餐/订购 ─→ 阶段6 开通 ────────────┤
                                                                    ↓
                                                            阶段7 三端页面
                                                                    │
                     阶段8 工单 ─→ 阶段9 聚合/趋势 ─→ 阶段10 部署/压测/验收
```

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 租户过滤漏接口 | 越权读数据，验收第 4 条直接挂 | 阶段 1 建立"接口清单 + 逐条回归"表，每个里程碑复测 |
| 开通流程与采集链路耦合 | 新大棚开通后不出数据 | 开通完成必须刷新配置快照并触发连接，做成一条可观测日志 |
| 页面数量多（三端十几页） | 交付延期 | 先做"登录 + 我的大棚 + 告警"三页跑通，再补商城与后台 |
| Modbus 寄存器映射调试耗时 | 阻塞阶段 3 | 先用固定寄存器表跑通，再抽象配置 |
| 逻辑删除后编码被占 | 无法重建同名设备 | 统一走"编辑 + 启用"恢复路径，页面给明确提示 |
| 套餐限额与实际设备不一致 | 开通后超卖 | 开通前在事务内校验，超额直接拒绝 |
| 单库多租户无数据库级隔离 | 一处 SQL 写错就串数据 | 所有查询集中到 Store 层，Controller 不直接拼 SQL |

## 7. 每阶段收尾动作

1. 跑通该阶段完成标准，留一条可复现的验证记录（命令或页面路径）。
2. 更新需求文档第 9 节对应验收项的勾选状态。
3. 在 `项目笔记.md` 补一段决策代价，例如：为什么越权统一返回 404、为什么开通要刷新配置快照、为什么事件型测点不节流。
